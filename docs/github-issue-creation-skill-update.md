# GitHub Issue Creation Skill Update (2026-02-15)

## Purpose

This update clarifies how the `github-issue-creation` skill should be used for this repo, especially with the new planning pipeline (Step 12) that can generate and optionally create GitHub issues automatically.

## Why this changed

- Step 12 in `docs/planning-build-steps.md` adds a planning artifact mode:
  - `plan_only` (artifacts only)
  - `plan_and_create_issues` (synthesize artifacts + create GitHub issues)
- The planning worker now writes artifacts and then creates issues from `ISSUES.json` when requested.
- Agents creating follow-up implementation issues must now align with both the planning output and the repository issue conventions.

## Canonical skill reference

- Use this skill as the source of truth:  
  `~/.codex/skills/github-issue-creation/SKILL.md`
- AGENTS now explicitly points issue-creators to this skill in `appforge-poc/AGENTS.md`.

## Alignment with repo conventions

### When to use this skill

- Any planning follow-up ticketization
- Any manually curated implementation split of Step 12 outcomes
- Cross-repo work that needs explicit dependency and repository boundaries

### Required issue characteristics

Keep issue bodies high-signal and modular:

- Exact target repository
- Clear objective and acceptance criteria
- Explicit context (docs, references, links)
- Dependency notes (including blocking/blocked-by constraints)
- Explicit labels:
  - exactly one `difficulty:*`
  - one of `agent:local`, `agent:remote`, or `developer` as required

### Recommended workflow for planning outputs

1. Run planning in `plan_and_create_issues` mode only when you are ready for issue creation.
2. Validate generated `ISSUES.json` for:
   - stable `id` values
   - valid `repo` format (`owner/name`)
   - valid dependency references
3. If creating issues manually:
   - preserve the generated dependency ordering or annotate blockers clearly
   - reuse deterministic titles and scope from the planning payload

## Suggested issue body contract (applies to this repo)

At minimum include:

- `## Target Repository`
- `## Description`
- `## Acceptance Criteria`
- `## Implementation Notes`
- `## Related Issues`
- `## Dependencies` (if any)

For generated issues, the planning writer adds a blocker section automatically in the issue body; manual follow-ups should mirror that structure.

## Step 12 cross-check

When planning issues are generated by the worker:

- Confirm these fields are present in session events:
  - `issues_written` (payload includes `requested_count` + `created`)
  - final `done` payload includes `issue_created_count`
- Confirm issue lifecycle stage names:
  - `planning_issue_writer`
